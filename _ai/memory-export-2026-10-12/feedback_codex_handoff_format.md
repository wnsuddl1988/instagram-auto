**최우선 — Cross Review 결과를 출력한 직후 (반복 위반, 2026-08-08 3회째 재지적):**
검수(PASS/NEEDS_FIX/BLOCKED)를 보고하는 turn은 **그 turn 자체에 블록형
인수인계서가 포함되지 않으면 미완료**로 취급한다. "검수 결과 보고"와
"Codex 인수인계서 출력"은 하나의 turn 안에서 분리되지 않는 단일 작업이다.
Owner가 "인수인계서 줘", "추천작업 뭐냐" 등으로 다시 물어보게 만들면
그 자체가 규칙 위반의 증거다. 검수 verdict를 출력하는 마지막 문장 다음에
빈 줄 하나만 두고 바로 인수인계서 블록을 시작한다 — "다음 턴에 요청하면 드리겠다"류의
지연은 없다. 매 Cross Review 응답마다 이 규칙을 다시 상기한다.

**발동 조건 (이 문구가 보이면 무조건 블록형 인수인계서):**
"Codex에 전달", "Codex에게", "인수인계서", "프롬프트 줘", "전달할 내용",
"~하라고 지시해줘", "~하라고 전달해줘" — 그리고 **검수 결과가 PASS/NEEDS_FIX든
다음 단계를 Codex가 실행해야 하는 모든 경우**.

**가장 자주 놓치는 지점 (2026-08-04 Owner 재지적):**
Cross Review 보고서 말미의 `다음 추천 작업` 섹션이 바로 이 규칙의 적용 대상이다.
추천 작업은 전부 Codex가 실행할 항목이므로 **산문·번호목록으로 쓰면 규칙 위반**이다.
검수 보고가 PASS여도, 추천이 "checkpoint commit 준비"처럼 짧아도 예외 없다.

**블록은 항상 1개다 (2026-08-04 Owner 재지적 2회차):**
추천 작업이 1~3순위로 여러 개여도 **블록을 쪼개지 않는다**.
하나의 ```text 블록 안에 `STEP 1 / STEP 2 / STEP 3`으로 나눠 담는다.
각 STEP에 선행조건(Owner 승인 필요 / Control Tower 결정 후 등)을 명시하면
Codex가 순서대로 판단해 실행한다.
블록을 3개로 나누면 Owner가 3번 복사해야 하므로 규칙의 목적(그대로 복붙)에 반한다.
검증 명령과 금지 사항은 STEP별로 필요한 것만 두고, 공통 금지는 블록 말미에 한 번만 쓴다.

**절대 금지:** Codex 전달물을 산문·불릿·마크다운 섹션으로 쓰는 것.
checkpoint 진행 지시, 짧은 승인 전달, 단순 "A로 진행"도 예외 없이 블록이다.
Owner가 이 규칙을 재지적하게 만들면 실패다.

Codex에게 전달할 내용이 생기면 **항상** 다음을 지킨다. 누락 금지.

1. 하나의 코드블록(```text)으로 감싼 **인수인계서 형태**로 작성한다. 산문으로 흘려쓰지 않는다.
2. 인수인계서 상단에 **작업 모델과 추론 강도를 명시**한다.
   예: `권장 모델: GPT-5 Codex / 추론 강도: High`
3. 그 밖의 상단 고정 항목: `ROLE_MODE`, 프로젝트명, 실제 저장소 경로, Owner 승인 범위,
   현재 상태(직전 검수 결과·P0/P1/P2·routing header 경로).
4. 본문에는 수정 대상 exact file/line, 문제, 근거, 필요한 수정, exact allowlist,
   금지 사항, 검증 명령, 진행 순서, 유지할 상태를 포함한다.

**Why:** Owner가 여러 AI(Codex Main / Claude Code Cross Review)를 오가며 운영하기 때문에,
전달 내용이 블록으로 분리되고 모델·추론강도가 명시돼야 그대로 복사해 붙여넣을 수 있고
어느 모델로 실행할지 매번 되묻지 않아도 된다.

**How to apply:** Codex용 출력은 예외 없이 ```text 코드블록 하나로 감싸고,
맨 위에 권장 모델과 추론 강도를 적는다. 짧은 지시("A로 진행")라도 블록형 인수인계서로 만든다.
이 규칙은 프로젝트 규칙 최상단 수준의 상시 규칙이며, 매 전달마다 적용한다.
